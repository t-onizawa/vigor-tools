# VIGOR MATSURI — 詳細ページ テンプレート化方針

```
Version: 0.3
Created: 2026-07-27
Updated: 2026-07-27
Scope: 石岡のおまつり1件を共通構造へ移行するところまで。
       8件展開・一覧ページ・絞り込みページは対象外。
```

石岡のおまつりのプロトタイプ（`matsuri/festivals/ishioka-omatsuri/`）を
8件展開する前に、共通化すべき部分と祭りごとに残す部分を整理する。
フレームワーク・ビルドツールは導入せず、GitHub Pagesでそのまま動く
静的構成を維持する。

---

## 1. 現状4ファイルの構造レビュー

| ファイル | 現状 |
|---|---|
| `style.css` | **石岡固有の記述なし。** 色・レイアウト・バッジ表現まで完全に汎用 |
| `script.js` | **ほぼ完全にデータ駆動。** グローバル変数`FESTIVAL`（`data.js`が定義）を読むだけで、石岡固有のロジックは一切ない |
| `index.html` | 骨格（各セクションのid構造）はほぼ汎用。`<title>`タグと`data.js`への参照のみが個別 |
| `data.js` | 完全に石岡固有 |

つまり現状のscript.js／style.cssは、**すでに実質「共通コンポーネント」
として書かれている**。8件展開に向けた作業は「新しい共通ロジックを
書く」ことではなく、「すでに汎用な2ファイルを共有できる場所に
物理的に移す」ことが中心になる。

### レビューで見つかった2つの不備

1. **`highlightComment`（一言見どころコメント）のレンダリングコードが
   存在しない。** `data.js`にはフィールドがあるが、石岡の値が`null`
   だったため、`script.js`にも`index.html`にも対応するセクションが
   一度も作られていない。「値があれば表示、`null`なら非表示」という
   設計（schema-design.md）はまだ実装されていない。8件展開前に
   実装が必要（次のCodexプロンプトに含める）。

2. **`renderAtmosphereMedia()`は`type === "youtube"`のみ対応。**
   Instagram・TikTokの場合は無条件でセクションごと削除される
   （沈黙のフォールバック）。現時点でInstagram/TikTokの採用候補が
   ないため今回は対応を広げず、**「YouTube以外は今のところ未対応」
   と明記した上で据え置く**（過剰設計を避けるため、需要が出てから拡張）。

## 4. 過剰設計・複雑化リスクの確認

以下は**やらない**。

- ビルドツール・バンドラー（Webpack/Vite等）やフレームワークの導入
- 汎用的な「JSONを渡せば何でも描画できる」レンダリングエンジン化
  （VIGOR MATSURIのスキーマ専用のシンプルな関数群のままにする）
- `index.html`の骨格までJavaScriptで完全自動生成すること
  （祭り8件程度の規模では、HTMLを複製する方が人間が中身を目で
  確認しやすく、壊れたときの原因も追いやすい。完全自動生成は
  「id属性の対応関係がコードの中でしか分からない」状態を生み、
  非エンジニアが今後手を入れる余地を狭める）
- CSSのユーティリティクラス化・独自デザインシステム化

**残るリスク：** `index.html`を祭りごとに手でコピーするため、id属性の
typoが起きると`shared/festival-detail.js`側は該当要素を見つけられず
黙って例外を投げる（`document.getElementById`が`null`を返し、
`.textContent`アクセスでエラーになる）。8件規模ではこのエラーは
ブラウザのコンソールに出るため気づけると判断し、追加の検証機構は
今回作らない。祭りの件数が大きく増えた場合に再検討する。

## 7. 終了済み等ステータス表示の改善案（設計のみ、共通JS未実装）

### 経緯

佐原の大祭 夏祭り（`eventStatus: "ended"`）を実装しレビューした結果、
見出し「{年}年の開催日」＋「終了」バッジの組み合わせは事実として
誤りではないが、「終了した祭りの情報を見ている」ことが伝わりにくく、
改善余地があるとの指摘があった。

**判断基準の整理：** VIGOR MATSURIは情報ディレクトリであり、
VIGOR TOOLSの判断ツール原則（Tool Principleほか、決断支援ツール
固有のルール）はそのまま適用しない。本節の判断基準は、CONCEPT.mdの
「開催確認ステータスは必要以上に複雑にせず、意味を混同させない」
という方針、および一般的な分かりやすさ（保証できない情報を
書かない、リンクを重複させない）に基づく。

### 見出し・補足テキストの対応表（全6ステータス）

| eventStatus | 見出し文言 | 日付近くの補足テキスト | バッジ文言（変更なし） |
|---|---|---|---|
| `confirmed` | {年}年の開催日 | なし | 開催確認済み |
| `scheduled_pending_official` | {年}年の開催予定 | 公式の詳細発表を確認中です | 開催予定・公式詳細待ち |
| `unconfirmed` | {年}年の開催情報 | 日程は未確認です | 未確認 |
| `cancelled` | {年}年の開催予定 | この開催は中止になりました | 中止 |
| `postponed` | {年}年の開催予定 | この開催は延期になりました | 延期 |
| `ended` | {年}年の開催実績 | この開催は終了しました | 終了 |

**`confirmed`にのみ補足テキストを付けない理由：** 唯一「公式に確定した
日程がそのまま確定情報である」状態であり、バッジ単体で意味が伝わる。
他5ステータスは、日付が「まだ確定でない」「もう有効でない」等の
留保が付く状態のため、見出し・補足テキストの両方で明示する。

### 次回開催情報の扱い（今回は実装対象外）

「次回の開催情報は未確認です」の表示は、**今回の実装範囲から外す。**
複数年度から表示対象を選ぶルール（下記参照）が未確定の段階で
先に出すと、将来的に開催予定ページにまで不要な「次回情報」が
表示されてしまう可能性があるため。`eventStatus`に応じた見出し・
補足テキストの動的表示のみを今回の実装対象とする。

### リンクの扱い

新しいリンク・ボタンは追加しない。既存の「出典・確認日」セクションが
公式情報へのリンクをすでに提示しているため、見出し付近に重複した
リンクは置かない。

### 複数年度の表示対象選定ルール（将来方針、実装は行わない）

`yearlyInfo`配列が複数年のエントリを持つケース（例：2026年`ended`と
2027年`confirmed`が同時に存在する）に備え、どのエントリを「表示対象」
として選ぶかの方針だけを先に記録しておく。**今回はこのロジックを
実装しない**（`yearlyInfo`が1件しかない現状では選定ロジック自体が
不要なため）。

```
1. 配列の先頭固定にはしない（現状の yearlyInfo[0] 決め打ちを廃止する）
2. 現在年のエントリがあれば、それを優先する
3. 現在年がなければ、未来年のうち最も近い年を選ぶ
4. 未来年もなければ、過去年のうち最も新しい年を選ぶ
5. 配列内の並び順には依存しない（登録順ではなく年の値で判定する）
```

8件展開の過程で実際に複数年エントリを持つ祭りが出てきた時点で、
このルールに基づいた選定ロジックを実装する。

### 実装への影響（今回のCodexプロンプトの対象）

- `matsuri/shared/festival-detail.js`に、`eventStatus`から見出し
  文言・補足テキストを引く小さなルックアップテーブルを追加する
  （既存の`eventStatusLabels`と同じパターンで実装できる想定）
- 見出し要素（現在は固定文言`id="dates-heading"`）を`eventStatus`に
  応じて書き換える。補足テキストは新しい要素を追加して表示する
- 複数年度の選定ロジック（上記）は実装しない。引き続き
  `yearlyInfo[0]`を参照する現状の実装のままでよい
- `data.js`側のスキーマ変更は不要（`schema-design.md`の改訂は伴わない）
- 石岡のおまつり（`scheduled_pending_official`）・佐原の大祭 夏祭り
  （`ended`）の両方で表示回帰がないことを確認してから適用する

### この案のリスク・留意点

- 見出し文言がステータスによって変わることで、詳細ページの
  情報順序（`schema-design.md`「詳細ページの情報順序」）自体は
  変わらないが、「1. 祭り名・エリア」の次に来る要素の文言が固定
  でなくなる。8件展開時に見出しパターンが増えすぎないよう、
  今回定義した6パターン以上には広げない
- `yearlyInfo`が複数年ぶんのエントリを持つケース（例：2026年`ended`
  ＋2027年`confirmed`が同時に存在する）の選定方針は上記「複数年度の
  表示対象選定ルール」で定義したが、**実装は伴っていない。**
  実装するまでは`yearlyInfo[0]`決め打ちのままなので、複数年エントリ
  を持つ祭りを8件展開の過程で追加する際は、この節を先に読むこと

## この文書の使い方

- 8件展開時の実装方針に迷ったとき → 本書の「共通化候補への対応状況」
- 新しい共通化候補が出てきたとき → 本書に追記し、過剰設計リスクの
  確認を必ず行ってから着手する
- スキーマそのものの変更は本書ではなく `schema-design.md` を参照
