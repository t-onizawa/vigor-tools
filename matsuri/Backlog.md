## 中長期戦略ロードマップ（2026-08-05 Founder承認）

100件が視野に入ったタイミングで、「件数を増やす／既存ページを育てる／
新機能へ投資する」という3択をPMが整理し、Founder承認を得た。**結論は
三択のどれか一つを選ぶことではなく、GA4計測基盤の確立を最優先の前提と
した上で、Phase順に進める**というもの。同時に複数の重い判断をしない、
という一人運営前提の規律をロードマップの中心に置く。

### Phase構成

```
Phase 0：GA4内部アクセス除外は統括担当の進行を待つ（最優先・進行中）
Phase 1：週次の祭り追加を週2〜3件程度で継続（Phase 0と並行可）
Phase 2：backgroundImage不足と「画像・動画の両方なし」の改善
         （Phase 0と並行可、atmosphereMediaは対象外）
Phase 3：内部アクセス除外後、クリーンなデータを2〜4週間蓄積して評価
         （Phase 0完了が前提）
Phase 4：Phase 3の結果を見て新機能を再検討（Phase 3完了が前提）
Phase 5：関東エリア完了を受け、全国展開を開始（2026-08-14着手決定）。
         次エリアは東北。以降は地方単位（東北→中部→近畿…）で順次
         展開する。GA4整備（Phase 0/3）とは独立した並行トラックであり、
         Phase 0完了を待たない（詳細は下記「全国展開（東北エリア）
         着手決定」参照）
```

### 追加方針（数値目標）

- **backgroundImage**：43.6%（34/78）→60〜65%を目標とする
- **atmosphereMedia**：53.8%（42/78）で既存の中長期天井目標
  （55%程度）にほぼ到達しているため、追加調査の優先度を下げる
  （Phase 2の対象外）
- **「画像・動画の両方なし」**：22/78件→15件程度まで削減を主目標とする
- **エリア完了目標**：関東エリア（既存7都県）は98件で掲載対象が
  一通り揃い、2026-08-14に完了と判定した。**主語は件数ではなく
  エリア完了**であり、95〜100件前後は当時の目安値に過ぎなかった。
  **関東完了を受け、全国展開（次エリア＝東北）に着手する**（詳細は
  下記「全国展開（東北エリア）着手決定」参照、2026-08-14改訂。
  一時「Phase 0完了まで保留」としたが同日中に撤回した）
- **体験タグ・フィルター化・新機能**：クリーンな計測データが揃うまで
  （Phase 3完了まで）着手しない

### 関東エリア完了ゲート（エリア完了時のFounder Review、
    2026-08-12追加・2026-08-12ゲート機構を修正・主語をエリア完了へ一般化）

関東エリア（既存7都県）の掲載対象が一通り揃うことが「関東版の一区切り」
であり、固定の件数ゴールでも新規追加の恒久停止でもない。VIGOR MATSURIは
関東で終わるプロダクトではなく、将来的な全国網羅（東北・甲信越・東海・
関西…）を目標とする前提のもと、**「関東エリアの掲載対象が完了する」
ことそのもの**を「次フェーズへの判断点」と位置づける。**95〜100件前後
という数字は、現時点で見積もっている目安値であり、判断の主語ではない。**
将来エリアを追加する際も、そのエリアごとに掲載対象の完了を都度見積もり、
同じ「エリア完了ゲート」のパターンを適用する（次のエリアで再び「100件」
という数字を使うわけではない）。

**ゲートの動かし方：** 関東エリアの掲載対象が完了する回であっても、その
回の追加処理（調査・検証・テスト・commit・push）は通常どおり最後まで
完了させる。取得・検証済みのデータを未commitのまま切り捨てることは
しない。その回の完了報告に「関東エリア完了。Founder Review待ち」と
記録し、**次回以降**の新規追加タスクを一時停止する。停止は恒久的では
なく、Founder Review実施後に再開するためのゲート。

一時停止した状態で、以下を確認するFounder Reviewを実施する。

```
- Search Console・GA4の状況（Phase 0〜3の進捗含む）
- 品質（backgroundImage・atmosphereMedia・両方なし件数）
- 運用負荷（一人運営で継続できているか）
- 自動化の成熟度（新規追加・整合性チェック・品質改善タスクの実績）
- データ構造が全国展開に耐えられるか（都道府県以外の地域区分・
  schema上の制約の有無）
- 次フェーズ（東北・甲信越など）へ進める状態か
```

レビュー結果を踏まえてRoadmap・Backlogを更新し、全国展開へ進むか、
関東内での深化（Phase 2〜4）を継続するかを判断する。Phase 0〜4の
GA4計測トラックとは独立した軸だが、Founder ReviewではPhase 3の
進捗状況も確認材料に含める（Phase 3が未完了のまま100件前後に到達した
場合、レビュー結果が「全国展開は保留、GA4クリーンデータ待ち」と
なることも起こり得る）。

### 全国展開（東北エリア）着手決定（2026-08-14、上記結論を撤回）

上記のFounder Review直後、Founderから「関東を完全に埋めてから全国へ」
という順番自体にこだわる必要があるか、という再検討の依頼を受けた。
PMとして論点を洗い直した結果、以下の理由で保留の結論を撤回し、
**全国展開（次エリア＝東北）に着手する**方針へ改めた。

**撤回の理由：**

```
- GA4整備（Phase 0）は、IPベースの除外方式からanalytics.jsの
  localStorage方式へ切り替える形で並行して動き出しており、
  「12日間停止」という前提が変わった
- 「Search Console/GA4で需要を見る」という当初理由は、全国展開の
  可否そのものを止めるゲートではなく、優先順位づけの材料だったと
  再整理した。GA4が汚れていてもSearch Consoleの実データ（八王子
  まつり・日立風流物等の順位の兆し）はこれまでも使用してきており、
  それ自体は利用可能
- 品質・運用負荷・自動化の成熟度・データ構造（フィルターUIの
  optgroup化）は、直前のFounder Reviewで確認済み（問題なし）
```

**全国展開の進め方：** 全国から品質基準だけで散発的に拾う方式ではなく、
**地方単位（東北→中部→近畿…）で段階的に広げる方式を採用する。**
理由は、(1) optgroup化した都道府県フィルターの構造上、地方単位で
進めた方がすぐに実用的な密度になる（1県1件のような虫食い状態を
避けられる）、(2) 関東で確立した「エリア内密度を埋める→候補が
尽きたら次へ」という運用のリズムをそのまま使い回せる、(3) エリアの
中で知名度・検索需要の高い看板祭りから着手すれば、Founderが重視する
「有名祭りの需要」も同時に満たせる、の3点。

**次エリア＝東北（6県）：**

```
青森県 aomori／岩手県 iwate／宮城県 miyagi／
秋田県 akita／山形県 yamagata／福島県 fukushima
```

`areaTag`の値はこの表記に統一する（既存の関東7都県と同じ命名規則＝
ローマ字小文字）。新しい都道府県の祭りを初めて追加する際、
`index.html`の都道府県フィルターに`<optgroup label="東北">`を新設し、
該当県の`<option>`を追加する（関東と同様、スキーマ側の変更は不要）。

**全国展開でも維持するルール：**

```
- 一次情報での裏取りを引き続き徹底する（有名祭りほど二次情報・
  まとめサイトが溢れるため、検索結果の要約だけで確定しない原則が
  むしろ重要になる）
- backgroundImage/atmosphereMediaの採用基準を、動画候補が多くても
  緩めない・数合わせしない
- エリア単位で密度を作ってから次へ進み、1都道府県だけ虫食い状態の
  まま放置しない
- 「サイトが祭りの価値を判定しない」というCONCEPT.mdの設計思想を
  維持し、有名祭りでも煽り文言を書かない
- 情報量・網羅性そのものを目的化しない
```

**今後のエリア間の遷移について：** 「全国展開に進むかどうか」という
戦略判断は今回のFounder Reviewで解決済みのため、今後東北→中部等の
エリア間遷移では、今回と同じ重さの6項目Founder Reviewは必須としない。
関東で確立した「エリア完了ゲート」の完了報告パターン（候補枯渇→
その回は完了させてから次回以降一時停止→簡単な状況報告）を踏襲し、
軽い確認で次エリアへ進めることとする。

### 全国展開ペースの見直し：「深く埋めてから次へ」→「浅く広く先に、深めるのは後で」（2026-08-18）

東北着手から4営業日（08-14, 17, 18）で9件（6県に最低1件）まで
進んだ時点で、Founderから「このペースだと1地方1ヶ月ペースになり、
全国網羅に半年前後かかるのでは」という懸念が出た。試算したところ
妥当な懸念だった：上記「全国展開の進め方」で採用した「地方内の密度を
関東同等（1県あたり約14件）まで埋めてから次へ」という基準は、深さを
優先するあまり広さ（全国に一通り行き渡るまでの時間）を犠牲にしていた。

**方針転換：地方の完了基準を「候補枯渇」に加えて「初期カバレッジ
（都道府県あたり3件）到達」でも成立させる。** 3件という数字に届いた
時点で深掘りを止めて次の地方へ進み、深める作業（関東同等の密度まで
増やす）は8地方すべての初期カバレッジが済んだ後にまとめて行う
（既存の「全国完了時」節で定義済みの、取りこぼし候補・新規公開候補・
過去保留候補を全国から再確認する運用フェーズがそのまま「深める」
フェーズとして機能する。これは新設ではなく、当初から用意していた
設計をそのまま使う形になった）。

「エリア単位で密度を作ってから次へ進み、1都道府県だけ虫食い状態の
まま放置しない」という直前の方針（本節冒頭「全国展開でも維持する
ルール」参照）とは、"密度を作る"の意味を「関東並みの深さ」から
「初期カバレッジ3件」へ引き下げる形で整合させた。虫食い状態
（0件の県を放置する）を避ける、という趣旨自体は変えていない。

**あわせて処理量も引き上げた：**

```
新規追加：1回あたり最大3件→5件（上限でありノルマではない、変更なし）
週次品質改善：調査12件/回→18件/回（週2回のまま、週24件→36件）。
              反映のソフトアラート閾値も8件→12件に比例調整
```

新規追加が5件/日・全国広範囲になり品質未着手の新規祭りが増えるペースが
上がるため、品質改善側も同じ比率（×1.5）で引き上げ、関東で起きた
「新規追加が品質改善に追いつかれない」状態の再発を防ぐ。

**試算：** 残り34県（中部・近畿・中国・四国・九州沖縄・北海道）に
初期カバレッジ（3件/県）を行き渡らせるには約111件必要。5件/日
（週25件）なら約4.5週間で全国に一通り行き渡る計算になり、「1地方
1ヶ月」から大幅に短縮できる見込み。

### sitemap.xml自己登録の再有効化・未登録26件の発覚（2026-08-18）

週次品質改善タスクの完了報告（commit `125db23`）で「sitemap未登録が
26件」と参考情報が上がり、確認したところsitemap.xmlの登録数86件に
対し実際の掲載数112件で、差分26件が正確に一致した。

**原因：** 2026-08-07に確立した「新規追加タスクが自分の作成分だけ
自己登録してよい」という例外（root CLAUDE.md）が、現在稼働している
新規追加タスクのプロンプトでは`sitemap.xml`が「変更禁止」に含まれる
形に戻っており、機能していなかった。完了報告にURLを記載するのみで
誰も拾って登録していなかったため、東北着手（2026-08-14）以降の
追加分がすべて未登録のまま積み上がっていた。11件登録漏れ
（2026-08-07）と同種の再発。

**対応：**
- 今後の再発防止として、新規追加タスクのプロンプトを修正し、
  sitemap.xmlを「変更禁止」から外して自己登録の例外条件（自分の
  作成分のみ・既存テンプレート踏襲・並び替え/削除/一括登録は対象外）
  を明記し直した。Founderが実際のScheduled Taskへ反映済み
- 既存の未登録26件は、同一回で自己作成した分ではない一括登録に
  あたるため例外の対象外。統括担当への一括登録依頼が必要（本件は
  matsuri担当範囲外のため、PMからは直接対応できない）

## 週次品質改善・自動反映（2026-08-12 設計確定）

**背景：** 95件時点の独立集計（data.js直接再集計）は、backgroundImage
48/95（50.5%）、atmosphereMedia 44/95（46.3%）、両方なし29件。
Phase 2完了直後の両方なし22/80（27.5%）から悪化しており
（29/95＝30.5%）、原因はPhase 1の週次新規祭り追加（素材確認なしで
公開する方針）が、不定期の手動Phase 2バッチより速いペースで
「両方なし」を積み増しているため。手動バッチ頼みでは追いつかない
という実測が、以下の自動化着手の根拠になった。

**役割分離：** 既存の「週次データ整合性チェック・自動反映」とは統合せず、
担当フィールドを完全に分離する。整合性チェック＝日程・eventStatus・
confirmation・出典等の**正確性フィールド**を検出・修正するタスク。
週次品質改善＝backgroundImage・atmosphereMediaの**素材フィールドのみ**
を探索・追加する加算的タスク。品質改善が整合性領域の問題に気づいても
修正はせず、完了報告に参考情報として記載するだけに留める（越境禁止）。
これにより従来の「週次品質監査」（実質は直近7日の新規祭りに対する
整合性チェックの縮小版で、担当領域が重複していた）を廃止し、
「週次品質改善」として役割を入れ替えた。

**採用基準：** atmosphere-media-guide.mdの既存基準（7節＝backgroundImage、
1〜6節＝atmosphereMedia）をそのまま適用し、自動化のために緩和しない。
「明確に基準を満たす」場合のみ自動反映し、境界事例（ロゴ・バナーの
大きさが微妙、チャンネルの実在性に確信が持てない等）は自動反映せず
レビュー候補として報告する。館林まつりの事例（research記録の文言が
画像実態と不一致だった）を教訓に、**research記録の文言と実際の
画像・動画内容が一致していることをコミット前の必須検証項目に追加した。**

**優先順位・件数：** atmosphereMediaは新規に別動画を探索せず、
backgroundImage調査中に見つかった候補が基準を満たす場合のみ判定する
（Phase 2の「backgroundImage優先・atmosphereMediaは対象外」方針を
維持）。選定順位は(1) 未調査の「両方なし」祭り (2) 前回調査から
4週間以上経過した「両方なし」祭り (3) 直近4週間以内に不採用判定済みの
祭りは除外。

**件数の再設計（2026-08-12、平日新規祭り追加ペース再評価を反映）：**
平日新規祭り追加が実質週15件相当（毎営業日3件の自動実行）で稼働して
おり、当初想定（週2〜3件）の5倍で動いていることが判明した。調査の
結果、新規追加タスク自体の実行品質は劣化していない（エラーの兆候なし。
唯一発生したsitemap.xml 11件登録漏れは自己登録ルール化〈2026-08-07〉
で構造的に解消済み）ため、**週2〜3件へ戻すことはせず、件数目標
「95〜100件程度」という既存の承認済みキャップをそのまま歯止めとして
機能させる方針とした。** 現在95件のため、このペースならキャップに
数日〜1週間で到達し、その時点で新規追加は一時停止してFounder Reviewを
待つ（2026-08-12改訂：「関東エリア完了ゲート」参照。当初は「穴埋め
中心へ自然減速」と記録したが、100件は停止ではなく次フェーズへの
レビューゲートという位置づけに修正した）。ロードマップの「週2〜3件」
という数値自体は書き換えない。

一方、15件/週ペースに完全追従する品質改善設計（週20〜25件調査）は、
過去の誤り事例（館林まつり・大原はだか祭りの誤判定）がより少ない
調査件数でも発生していたことを踏まえ、いきなりは採用せず、まず
**調査10件／週、反映は条件を満たした分だけ（安全弁として上限5件、
超過分は翌週へ繰越）** で初回実行した。

**初回実行結果（2026-08-12、commit `6f84cbc`）：** 調査3件（あびこ
カッパまつり・大田原屋台まつり・大田原与一まつり）に対し2件が基準を
満たしbackgroundImageを反映、1件は基準未達で不採用（research記録の
みnote化）。採用率67%。

**運用見直し（2026-08-12、Founderからの再検討依頼を反映）：** 初回
実行結果と実測ペース（新規追加が実質週15件、両方なし27/95）を踏まえ、
「反映件数」ではなく「調査件数」を制限する設計の方が効率的という
Founder提案を採用した。ただし週1回・調査10件から週2回・調査20件
（週40件）への一気の4倍増は、稼働実績が初回1回分しかない自動化に
対して急すぎると判断し、**段階的に引き上げる。**

```
新設計：週2回（火・金）、1回あたり調査12件（週24件）
反映：条件を満たした分だけ、件数上限なし
安全弁：1回の反映が8件を超えた場合、完了報告に明記し、
        次回実行前にPMレビューを挟む（反映自体は止めない）
再評価：3週間分（6回）の実績を見て、投入件数・頻度を再調整する
        （採用率が安定して高ければ20件/回への引き上げを検討）
```

計算根拠：現ペース（新規追加週15件、うち約2/6が調査中に自ら素材を
見つけている実績＝自己補完率33%）だと、両方なしは週10件前後純増する
見込み。週24件調査・採用率50〜60%と仮定すると週12〜14件解消でき、
純減ペース週4件前後。現在の両方なし27件は、この設計なら3週間ほどで
ロードマップの目標15件に近づく計算になる。週40件・上限なしという
当初提案は、必要以上に速いペース（1週間強で目標到達）かつ初回実行
1回分の実績しかない状態での急拡大になるため、まずは週24件で運用実績を
積む。

**「反映件数を制限しない」ことのリスクと対応：** 週次品質改善は
専用git worktreeからPRを介さず直接mainへpushする設計（整合性チェックと
同じモデル）のため、1回の実行で多数の誤りが発生した場合の露出が
反映件数の上限撤廃で理論上は増える。ただし各候補は独立に検証される
設計（1件の失敗が他候補の反映を止めない）のため、上限を設けても
「同じ基準の誤り」自体は防げない。上限の代わりに**8件超過時のソフト
アラート**でPMの目視確認を挟むことで、件数を人為的に切り詰めずに
安全性を確保する。

**役割分担の再確認：** 新規追加タスク＝新規祭り追加が目的、
backgroundImage/atmosphereMediaは調査中に見つかれば反映・無理に探さない。
品質改善タスク＝既存祭りの素材補完が目的、加えて調査中に見つかった
research記録の軽微な誤り（誤字・表記ゆれ等）の修正も反映してよい
（整合性チェック領域＝日程・eventStatus等には引き続き触れない）。
この分担は当初設計から変更なし。

**build・lintについて：** matsuriは静的サイト（HTML/CSS/JS、外部API・
ビルドツールなし、VIGOR LAB共通方針）のため、buildステップ・lintツール
自体が存在しない。既存の検証項目（node --check、git diff --check、
モバイル390×844/デスクトップ1440×900での実機確認、console error
確認）が実質的な「テスト」に相当し、これをそのまま維持する。存在しない
build/lintコマンドをプロンプトに含めない。

**検証・反映：** 専用git worktree・matsuri外への越境禁止・PR不使用・
auto-merge不使用は整合性チェックと同じモデルを踏襲。ただし品質改善は
「見つかったものだけ足す」加算的作業のため、候補ごとに独立して
検証し、1件の検証失敗が他の合格候補の反映を止めない設計とした
（整合性チェックは「間違いを直す」性質上、全体停止が安全側になる
ため、この点は意図的に運用モデルを変えている）。

確定した最終プロンプトは、次回Scheduled Task更新時にそのまま使用する。

**実際に稼働しているプロンプトとの乖離を発見・修正（2026-08-18）：**
Founderから実際に運用中のプロンプト全文が共有された結果、PM側で
把握していたBacklog記載版とは構成が異なっていることが判明した。

links/schemaの不整合を**修正して反映する**手順になっており、

- セクションがほとんど使われない場合の改善余地（期間・件数・見せ方の
  見直し候補）
- 上記を踏まえた継続・改善・撤去の判断

**凍結の例外（2026-08-04）：** レイアウト・配置のみの変更は凍結の

適用する。フィルターは下の一覧にのみ効く独立コンポーネントのため、
配置をその上に揃える方が構造上自然という判断。

「決める型」に関する外部での議論を受け、MATSURI内の小さな実験として
着手が決まった。新規プロジェクトの立ち上げではなく、既存75件のデータを

仮称だったが、選定ロジックの検討過程で「おすすめ」が主観評価語に
読めるリスクが判明し、`まもなく開催`へ改称した。

**方針（一貫して維持）：**
- 新規プロジェクトは立ち上げない。MATSURI内で小さく検証する
- CONCEPT.mdの思想（「サイトが祭りの価値を判定することはしない。
  判定するのは常にユーザー自身」）を崩さない
- 価値判断（editorial pick）ではなく、開催状況など既存データのみを
  使った機械的なレコメンドにする
- GA4で効果を計測し、結果次第で継続・縮小・終了を判断する

**選定ロジック確定の経緯：** 「今日の祭り」「次に開催される祭り」

**将来のSEO安定性向上候補（2026-07-29追加）：** JSON-LDの生成方式を、
現行の実行時生成（`festival-detail.js`がJSで`<head>`へ挿入）から、
静的HTMLへの事前埋め込み（ビルド時または手動で各`index.html`に

リスクが理論上ある。現時点では静的サイトの運用方針（ビルドツール
なし）と実装コストの観点から見送るが、SEO効果の実測結果次第で
再検討する候補として記録する。**現時点では対応不要。**

**geo（緯度経度）追加の将来検討（2026-07-29追加）：** schema.org/Event
導入時点（実装済み・commit予定）で、全28件の`mapReference.lat`/`lng`が

不要。`data.js`に実座標を入れるだけで反映される）。**現時点では対応不要。**
座標調査自体を優先着手する動機は今のところない（一次情報での座標確認は
コストが高く、`query`文字列ベースの地図表示で現状十分に機能している）。

### 将来ビジョン：カード・詳細ページの「雰囲気」表現（2026-07-29 Founder確認）

**実装（2026-07-29完了・重要な設計変更あり）：**
1. 一覧カードの右寄せ背景（左0%→右へフェード、上下は画像を拡大して
   レターボックスをクロップ）
2. 詳細ページのタイトルヒーロー背景（フル幅・ブラー・グラデーション
   オーバーレイで可読性確保）

**設計変更：`atmosphereMedia[0]`のサムネイル流用ではなく、独立フィールド
`constantInfo.backgroundImage`を新設した**（schema-design.md 設計原則
#12、atmosphere-media-guide.md 7節）。石岡・熊谷・八王子で実際に候補

が背景として優れている（文字なし・主役が明瞭）」ことが一致しない
ケースが多いと判明したため。公式・自治体チャンネルはタイトル文字入り
サムネイルが多く、文字なしの現地感あるサムネイルは個人チャンネルの
生ログ的投稿（動画としては極端に短い／長いなどatmosphereMediaの採用
基準を満たさない）に偏る傾向があった。backgroundImageの採用基準は
atmosphereMediaの基準を一切引き継がず、「主役が判別できる／文字が
支配的でない／実写である」の3条件のみで判断する。

現在の3件（石岡・熊谷・八王子）は、atmosphereMediaとは別の動画

backgroundImageとして採用済み。

**進め方：** 該当基準を満たす候補が見つかった祭りから順に対象が増える。
一気に全件対応を目指さない。Phase2優先3（川越・秩父・佐原）の
atmosphereMedia調査時も、backgroundImageは別途独立して調査する。

## 運用ルール

- 固定計画ではない。追加・削除・並び替えは自由。
- 各アイテムは仮説。公開後の反応で優先度が変わることを前提とする。
- 候補祭りの情報は登録前に必ず一次情報で裏取りする
  （未確認のまま断定表示しない。CONCEPT.mdの開催確認ステータス運用と整合させる）。
- 「情報がないものを無理に埋めない」「動画を数合わせで追加しない」
  「山車・踊り等の定義を曖昧にしない」という28祭り展開時の方針は、
  今後の追加・更新作業でも維持する。
- **出典を「404・到達不可」として除外する前に、必ず別の方法・タイミングで
  再確認する（2026-08-03追加）。** `curl -I`等でHTTPステータスを直接
  確認し、1回の取得失敗だけで断定しない。時間を空けた再試行でも到達
  不可なら、即削除せず「到達不可・要再確認」として`research/{slug}.md`
  に記録しつつ出典自体は残し、複数回の週次チェックで一貫して到達不可と
  確認できた場合のみ除外を検討する（週次データ整合性チェックPR #1で、
  実際には生きていた出典を404と誤判定して削除しかけた事例から追加した
  ルール）。
