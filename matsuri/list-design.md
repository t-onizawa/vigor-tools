# VIGOR MATSURI — 一覧ページ（matsuri/index.html）設計

```
Version: 0.2
Created: 2026-07-28
Updated: 2026-07-28
Scope: 一覧ページの最小設計のみ。実装はCodex CLIへ渡す。
       残り6件の登録・エリア別SEOページ・検索・地図・CMS・
       ビルドツールは対象外。
```

CONCEPT.mdの中心価値「行ってみたい祭りを、見つけやすくする」を、
現在実装済みの2件（石岡のおまつり・佐原の大祭 夏祭り）で不自然に
見えず、将来8件程度に増えても作り直しにならない形で一覧ページに
落とし込む。

---

## 0. 先に結論：技術的な制約が1つある（最重要）

設計に入る前に、実装上避けて通れない制約を明確にしておく。

現在、各祭りの`data.js`はすべて次の形で書かれている。

```js
const FESTIVAL = { ... };
```

詳細ページ（1ページ1`data.js`）ではこれで問題ないが、**一覧ページで
複数の祭りの`data.js`をそのまま`<script src="...">`で並べて読み込むと、
2つ目の`const FESTIVAL = ...`の時点でブラウザが
「識別子`FESTIVAL`は既に宣言されています」というエラーを出して
止まる。** `const`は同じ読み込み単位の中で再宣言できないため。

このため、「各詳細ページのdata.jsをそのまま一覧から読み込む」
（後述する推奨案）を実現するには、**単純に`<script>`タグを並べるの
ではなく、1件ずつ独立した実行スコープで読み込む**工夫が必要になる。
詳細は「7. データ管理」で扱う。既存の`data.js`・`festival-detail.js`・
既存2件の詳細ページには変更を加えない前提で解決できる。

## 1. 一覧ページの役割

「詳細ページを開かなくても比較できる」を実現するため、カードに
以下を持たせる（詳細は5節）。ただし全項目を同列に並べず、
**比較の意思決定に直結する情報を上位に、透明性のための情報
（出典・確認日等）は詳細ページに残す**、という優先順位を付ける。

## 2. 初期状態の設計

3案を比較する。

| 案 | 内容 | 評価 |
|---|---|---|
| A. カードのみ表示、絞り込みなし | 2件を並べるだけ | 過剰設計は避けられるが、後で絞り込みを追加する際に画面構成を作り直す可能性がある |
| B. 最初から最小限の絞り込みを表示 | 少数の条件を最初から出す | 2件では効果が薄いが、構成を作り直さずに済む |
| C. 件数に応じてUIを切り替える | 件数がN件を超えたら絞り込みを表示 | 分岐ロジック自体が複雑さの発生源になる。「N件」の閾値も根拠なく決めることになる |

**Cは採用しない。** 「何件になったら出すか」を決める根拠がなく、
分岐ロジックを後から書き換える羽目になりやすい（過剰設計そのもの）。

**採用案：Bを、ごく小さく実装する。** 検索窓・複数条件のフィルタ
フォームのような「重い」UIは今回作らない。その代わり、**最も価値が
高い1条件だけ**を軽量なトグル（チップ）として最初から置く
（3節で選定）。これなら2件時点でも不自然に見えず、8件に増えた
ときに新しい条件を追加してもレイアウトを作り直す必要がない
（同じチップ列に追加するだけで済む構造にする）。

あわせて、**カードのマークアップに`data-*`属性で判定用の値
（エリア・山車上の踊りの有無・見どころの時間帯・開催確認ステータス
のカテゴリ等）を最初から埋め込んでおく。** 今は使わない属性でも、
将来の絞り込み条件追加時にJS側のロジック追加だけで対応でき、
カードのHTML構造自体は変更しなくて済む。

## 3. 絞り込み条件（MVP候補4つ、優先順位付き）

CONCEPT.mdの候補（エリア・山車・神輿・踊り・曳き回し・昼夜・
駐車場・開催月）から、「祭りを選ぶ際の実際の価値」で絞り込む。

| 優先度 | 条件 | 選定理由 |
|---|---|---|
| 1 | これから開催される祭り（confirmed／scheduled_pending_officialのみ） | 一覧が育つほど「もう行けない祭り」が増える。行ける祭りだけを見たいという需要が最も時間とともに強くなる。実装コストも最小（対象2ステータスのみの真偽1条件） |
| 2 | 見どころの時間帯（昼／夜／両方） | Founderの当初の課題意識（「昼と夜のどちらが見どころか」）そのもの。石岡（夜）・佐原（昼・夜）で実際に値が分かれており、差別化要素として機能する |
| 3 | 山車の上で踊りがあるか | 同じくFounderの当初の課題意識（「山車の上で踊りがあるか」）そのもの。石岡（あり）・佐原（なし）で実際に値が分かれる |
| 4 | エリア（都道府県） | 対象地域が茨城・千葉・埼玉・東京の4県に広がるほど価値が増す。現時点では2県のみで判別力は低いが、カード上に都道府県名は既に表示されるため、専用コントロールがなくても視認は可能 |

**山車の有無・神輿の有無・曳き回しの有無・駐車場の有無・開催月は
今回のMVP条件から外す。** 理由：VIGOR MATSURIの掲載対象が
「山車祭りを中心に」（CONCEPT.md）絞られているため、山車・神輿・
曳き回しは今後もほぼ`true`で揃う可能性が高く、絞り込み条件としての
判別力が低い（実際、現在の2件はどちらも山車・神輿・曳き回しが
`true`で一致している）。駐車場・開催月は判断材料としての優先度が
相対的に低いと判断した。

### 今回のCodexプロンプトで実装するのは「優先度1」のみ

4条件すべてを設計候補として残すが、実際にUIとして実装するのは
**「これから開催される祭り」の1トグルだけ**にする。理由：
- 「必要最小限」を体現する最も明確な線引きになる
- 2件のうち佐原が`ended`のため、実際にトグルを動かすと表示件数が
  2→1に変わる、という**動作確認ができる最小のテストケース**になる
- 優先度2・3は`data-*`属性としてカードに埋め込んでおき、次のフェーズ
  （6〜8件到達時）でチップを追加する形で拡張する

**名称と対象ステータスを一致させる：** 「開催予定のみ表示」という
名称は`unconfirmed`（未確認）や`postponed`（延期）を含むのか曖昧に
なるため採用しない。ラベルは**「これから開催される祭り」**とし、
ONにしたときに表示対象とするのは`confirmed`と
`scheduled_pending_official`の**2ステータスのみ**とする。
`unconfirmed`・`postponed`・`cancelled`・`ended`はすべて非表示に
なる（4段階の「並び順」上はそれぞれ別の優先度を持つが、この
フィルタでは一括して除外する、というシンプルな二分法にする）。
延期後の日程が確定して`confirmed`に更新された場合は自然に
表示対象へ入るため、`postponed`を特別扱いする必要は今はない。
実データで「延期後に日程が確定したが元のpostponedのまま扱われて
困る」ようなケースが出てきた時点で、条件の拡張を検討する。

## 4. 開催状況と並び順

### 4-1. 表示対象年度の選定（複数年度時代への備え）

`yearlyInfo`は将来複数年のエントリを持てる設計だが、
`template-design.md`が定義した選定ルール（配列先頭に依存しない／
現在年優先／なければ未来年の最近接／それもなければ過去年の最新）は、
これまでどのページでも実装されていなかった。**一覧ページは
「先頭固定」で新しく作ってしまうと、`template-design.md`が
既に決めた方針と矛盾する実装を新規に生み出すことになるため、
一覧側は今回から本ルールを実装する。**

`getPrimaryYearlyInfo(festival)`関数を以下のロジックで実装する。

```
1. festival.yearlyInfo が配列でない、または空配列の場合
   → その祭りはエラー扱いとして一覧から除外し、
     console.warn に祭りID・理由を出力する
2. 各エントリの year が数値でないものは無効なエントリとして無視する
   （有効なエントリが1件も残らない場合は1と同様に除外する）
3. 有効なエントリの中に、year が「現在の年」と一致するものがあれば、
   それを採用する
4. 一致するものがなければ、year が「現在の年」より大きい
   （未来の）エントリのうち、最も年が小さいもの（最も近い未来）を
   採用する
5. 未来のエントリもなければ、year が「現在の年」より小さい
   （過去の）エントリのうち、最も年が大きいもの（最も新しい過去）を
   採用する
6. 「現在の年」は実行時の実際の年（例：new Date().getFullYear()）を
   使う。配列内の並び順には一切依存しない
```

現在、石岡・佐原とも`yearlyInfo`は2026年の1件のみだが、この
ロジックであれば「たまたま配列の0番目が正しい年だった」のではなく
「正しい選定ルールの結果として2026年が選ばれた」ことになり、
将来2件目のyearlyInfoが追加されても一覧側の実装を変えずに
正しく動く。

**詳細ページ側（`festival-detail.js`）への同ロジック導入は
今回の範囲外とする。** 詳細ページは引き続き`yearlyInfo[0]`の
直接参照のままで、今回は変更しない（ご指示どおり）。ただし
これにより、**一覧と詳細で異なる年度が表示されうる状態が
理論上発生する**（例：yearlyInfoが2件になった場合、一覧は
正しい年を選ぶが詳細ページは常に配列0番目を表示する）。
現時点ではどちらの祭りも1件しか`yearlyInfo`を持たないため
実害はないが、2件目のyearlyInfoを持つ祭りを追加する前に、
`festival-detail.js`側にも同じ選定ロジックを導入する必要がある
（`template-design.md`に既存の申し送りとして記録済み）。

### 4-2. 並び順ルール

`eventStatus`を4段階の「表示優先度グループ」に分け、グループ内は
日付で並べる。

| 優先度グループ | eventStatus | グループ内の並び |
|---|---|---|
| 0（最上位） | confirmed, scheduled_pending_official | 開催日が近い順（昇順） |
| 1 | unconfirmed | 開催日が分かる場合は近い順。分からない場合は末尾へ、同グループ内では祭り名の五十音順 |
| 2 | postponed | 開催日が近い順（分かる場合） |
| 3 | cancelled | 確認日が新しい順 |
| 4（最下位） | ended | 開催日が新しい順（降順＝直近に終わったものが上） |

**優先度の考え方：** 「これから行けるか」を基準にする。confirmed／
scheduled_pending_officialは今すぐ行動できる情報。postponedは
「いつかは開催される」ため中止より上。cancelledは今回は行けないが
情報として残す価値はあるためendedより上。endedは最も
「今すぐの行動」に結びつかないため最下位。

### カードに載せる／詳細ページに残す、の判断

| 情報 | 一覧カード | 判断理由 |
|---|---|---|
| 祭り名 | ○ | 必須 |
| 正式名称 | × | 比較に不要。詳細ページのみ |
| 都道府県 | ○ | エリア比較に必要 |
| 市区町村・地区 | × | カードでは都道府県までに留める（佐原の「香取市佐原（本宿地区）」は長く、カードでは冗長） |
| 日付 | ○（簡易表記） | 必須。ただし詳細ページのような曜日付き全日付列挙は長すぎるため簡易化する（下記） |
| 開催確認ステータス | ○（バッジ） | 必須。詳細ページと同じバッジデザインを流用 |
| 山車／神輿／踊り／曳き回し | ○（コンパクト表記） | 差別化の核。ただし詳細ページの大きなバッジではなく、1行のアイコン+ラベル程度に圧縮する |
| 昼／夜 | ○ | 差別化の核 |
| 駐車場 | ○（あり/なし/未確認のみ） | 比較に有用。ただし`parkingNote`の長文はカードに出さない |
| 一言見どころ | ○（値がある場合のみ） | CONCEPT.mdの想定どおり。**現状、石岡・佐原とも`highlightComment`が`null`のため、今回はどちらのカードにも表示されない**（別途、後述の懸念点を参照） |
| 動画の有無 | ○（あり／なしのみ、埋め込みなし） | 8節で詳述 |
| お囃子の特徴 | × | 文章が長く、カードには不向き。詳細ページのみ |
| 出典・確認日 | × | 透明性情報は詳細ページに委ねる |
| 「詳しく見る」導線 | ○ | カード全体をリンクにし、下部に矢印テキストを添える形を推奨（別要素のボタンにしない） |

### 日付の簡易表記

詳細ページは「2026/9/19(土) / 2026/9/20(日) / 2026/9/21(月)」と
個別列挙しているが、カードでは長すぎる。以下のような範囲表記に
圧縮することを提案する。

```
石岡：2026年9月19日(土)〜21日(月)
佐原：2026年7月10日(金)〜12日(日)
```

年をまたぐ・月をまたぐケースは今回の2件には存在しないため、
その場合の表記ルールは次フェーズ（6〜8件到達時）で決める。

### 懸念点：「一言見どころ」が現状どちらの祭りにも無い

CONCEPT.mdが重視する項目だが、石岡・佐原とも`highlightComment`は
`null`のまま（推測で埋めていないため）。一覧ページ自体は
「値があれば表示、なければその行を出さない」という、既存の
詳細ページと同じnull非表示の設計で問題なく動くが、**実際に
一覧を公開する前に、この2件だけでも事実ベースの一言見どころを
作成しておくと、一覧の完成度が上がる。** これは一覧ページの
実装課題ではなく、コンテンツ側の宿題として別途扱うことを推奨する。

## 6. 画面構成（モバイル優先、上から順）

```

   「VIGOR MATSURI」＋1〜2文の説明

```

デザインは既存詳細ページと同じ、白・黒・薄いグレー基調、
モバイル優先を維持する。

## 7. データ管理（推奨構成）

3案の比較。

| 案 | 内容 | 二重管理リスク | 実装コスト |
|---|---|---|---|
| A. 各詳細ページのdata.jsを一覧から複数読み込み | 一覧が既存data.jsをそのまま参照 | なし（単一の情報源） | 中（0節の技術的制約への対応が必要） |
| B. 一覧専用の軽量データファイルを作る | 一覧用に要約データを別途持つ | **高い**（詳細ページ更新時に一覧側の同期を忘れるリスクが常に残る） | 低 |
| C. 祭りデータを共通ディレクトリへ移動 | `festivals/`から`shared/data/`等へ移す | なし | 高（既存2件の詳細ページの参照パスを変更する必要があり、既存の実装レビュー済みファイルに手を入れることになる） |

**推奨：A。** Bは「データの二重管理は極力避ける」という方針に
真っ向から反する。Cは二重管理は避けられるが、既に実装・レビュー
済みの詳細ページ2件に不要な変更を加えることになり、リスクに
見合わない。

Aを実現する具体的な方法（0節の制約への対応）：

1. 一覧ページ用のJS（`matsuri/shared/festival-list.js`、新規）が、
   `fetch()`で各祭りの`data.js`を**テキストとして**取得する
2. 取得したテキストを`new Function(text + "; return FESTIVAL;")()`
   のような形で、**独立した関数スコープの中で実行**し、
   その戻り値として`FESTIVAL`オブジェクトを受け取る
   （関数呼び出しごとに新しいスコープが作られるため、
   `const FESTIVAL`の重複宣言エラーが起きない）
3. 既存の`data.js`・`festival-detail.js`・既存2件の`index.html`は
   **一切変更しない**

### `new Function`使用に関する明記事項（重要）

`new Function`は一般に「評価対象の文字列を実行コードとして扱う」
手法であり、何を評価するかを誤ると危険になりうる。今回の用途を
以下のとおり限定し、リスクを明確にしておく。

- **評価対象は、同一オリジン内・自分たちで管理している固定パスの
  `data.js`のみ**（`festivals/{既知のスラッグ}/data.js`）に限定する。
  外部URLから取得した内容や、ユーザー入力（検索語・URLパラメータ等）
  を評価対象にすることは絶対にしない
- ブラウザのContent Security Policy（CSP）で`unsafe-eval`相当が
  禁止されている環境では、`new Function`は動作しない。現時点の
  VIGOR MATSURI・VIGOR LAB全体でCSPは設定していないため今は問題
  ないが、将来CSPを導入する場合はこの一覧ページの読み込み方式を
  見直す必要がある
- **これは8件程度のMVP規模に限定した構成であり、恒久的な設計では
  ない。** 件数が大きく増える、CSPを導入する、複数の一覧ページ
  （エリア別等）が必要になる、といった変化があれば、
  ES Modules化（`data.js`に`export`を付け、詳細ページ側の読み込みも
  `type="module"`に統一する）や、共有データファイル化（8件を
  超えた際にビルド前提の構成へ移行する）を再検討する
- 各祭りの読み込みは「fetchの成功（`res.ok`を確認）」「取得した
  テキストの構文が正しいこと」「`new Function`実行時に例外が
  出ないこと」の3段階いずれかで失敗しうる。**どの段階で失敗しても、
  該当の祭りだけをスキップし、`console.warn`に祭りのスラッグと
  エラー内容を出力した上で、他の祭りの表示は継続する**
  （1件の不具合が一覧ページ全体を止めないようにする）

この方法は、いま持っている`data.js`をそのまま「単一の情報源」
として一覧・詳細の両方から使い回せる。唯一新たに必要になるのは、
「どの祭りフォルダを一覧に含めるか」という**フォルダ名のリスト
（祭りの内容そのものではない）**で、これは`festival-list.js`内に
小さな配列として持たせる。

```js
const FESTIVAL_SLUGS = ["ishioka-omatsuri", "sawara-natsu-matsuri"];
```

これは「データの二重管理」には当たらない。祭りの名前・日付・特徴
といった**内容**は一切複製しておらず、「どのフォルダを見に行くか」
という目次だけを持っているため。8件目以降を追加する際は、
この配列に1行追加するだけでよい。

**このアプローチは`file://`で直接開くと動かない**（`fetch`は
ローカルファイルへのCORS制限で失敗する）。GitHub Pagesでの本番
配信や、これまでのレビューで使ってきた`python3 -m http.server`
のようなローカルサーバー経由であれば問題なく動く。既存の詳細ページ
の動作確認方法と同じ制約であり、新たな運用負担は発生しない。

**今回は採用しない代替案（将来の検討候補として記録）：**
`data.js`を`data.json`に変え、`fetch`でJSONとして読み込む方式に
統一すれば`new Function`のような手法は不要になる。ただしこれは
既存2件の詳細ページの読み込み方式（`<script src="./data.js">`で
グローバル変数`FESTIVAL`を参照する現行方式）も合わせて変更する
必要があり、既に実装・レビュー済みのページへの影響が大きいため、
今回は見送る。8件を超えて一覧の仕組みが本格的に負荷を持ち始めた
タイミングで再検討する。

## 8. 動画（YouTube等）の一覧での扱い

ご指摘のとおり、YouTube公式プレーヤーを一覧に複数並べるのは
表示速度・視認性の観点で避ける。今回のMVPでは**画像・埋め込み
どちらも一覧カードには置かない**方針を提案する。

検討した代替案と不採用の理由：

- **YouTubeのサムネイル画像（`https://img.youtube.com/vi/{contentId}/...`）
  をカードに表示する案：** 技術的には可能（YouTube自身が配信する
  静的画像を参照するだけで、自サイトへの転載にはならない）。
  ただし、現状atmosphereMediaがあるのは石岡のみで、佐原にはない
  ため、2件中1件だけ画像が付く非対称なレイアウトになる。
  画像の有無で高さが揃わない・レイアウトが複雑化するリスクの
  わりに、2件時点での効果は小さいと判断し、今回は見送る
- **採用する案：** カード内に「動画あり」という、他の項目
  （「あり」「なし」等）とトーンを揃えたテキストのみ
  （atmosphereMediaが空でない場合のみ表示、ない場合は行ごと
  非表示）を1行添えるだけに留める。絵文字・アイコン画像は使わない。
  実際の動画はカードリンク先の詳細ページで見る

8件規模になり、複数の祭りに動画が揃った段階で、サムネイル表示を
再検討する（この場合も直接のYouTube埋め込みではなく、静止画
サムネイル＋詳細ページへのリンクという構成を維持する）。
