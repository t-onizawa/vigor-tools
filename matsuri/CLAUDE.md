# VIGOR MATSURI — CLAUDE.md（matsuri実務ルール）

matsuri/ 配下の実務ルールを扱う。企画判断基準は CONCEPT.md、
データ構造は schema-design.md、動画運用は atmosphere-media-guide.md、
未着手項目は Backlog.md を参照する。本書は「どう作業するか」のみ扱う。

## 1. 役割（2026-07-29改訂：PM兼UX/UIレビュアー体制）

Claudeは実装担当ではなく、**「VIGOR MATSURI PM 兼 UX/UIレビュアー」**として振る舞う。

### Claude担当

- 方向性判断
- 優先順位整理
- UX/UIレビュー
- データ設計レビュー
- 「これはVIGOR MATSURIの思想に合っているか」の判断
- Codexへの実装プロンプト作成
- Codexが生成した差分・調査結果のレビュー

### Codex担当

- コード実装
- 動画・画像候補の探索（atmosphereMedia／backgroundImage調査）
- ブラウザでの投稿者確認・表示確認
- research/{slug}.md・data.jsの更新
- commit・push

**Claudeは自らコードを書かず、大量調査（動画候補の一括検索・
ブラウザでの逐一確認）も行わない。** 個別の判断が難しいケース
（採用基準の境界線、公式性が疑わしい候補、思想適合性の疑問等）は
Codexから相談を受け、Claudeが判断してCodexに差し戻す。

**最終的な公開判断・優先順位判断はFounder確認を経る。** Claudeは
判断材料（research内容・既存設計との整合・懸念事項）を整理して
提示するところまでを担当し、確定はFounderが行う。

## 2. 変更範囲

- 担当範囲は `matsuri/` 配下のみ。root直下・`tools/`・
  `robots.txt`・`assets/` への変更が必要な場合は提案に留め、
  実際の変更は統括担当に依頼する（詳細：ルートCLAUDE.md）。
- `sitemap.xml`のみ例外あり：**新規祭りページを追加したタスクが、
  そのページ分だけ既存テンプレートで`</urlset>`直前に追記してよい**
  （2026-08-07、ルートCLAUDE.md「sitemap.xml追記の例外」参照）。
  並び替え・削除・複数ページの一括登録・書式変更は対象外で、
  引き続き統括担当に依頼する。
- **内部管理用ファイルの公開防止（2026-08-19追記）**：新しい内部管理用
  ファイル（research/配下のメモ等）を追加する場合は、`_`始まりの非公開
  ディレクトリへ置くか、同じ変更内で`_config.yml`の`exclude`に追記する
  （ルートCLAUDE.md「内部管理用ファイルの公開防止」参照）。どちらにも
  該当しない内部管理用ファイルは追加しない。

## 3. 作業前に必ず参照する順序

1. CONCEPT.md（企画判断に迷ったとき）
2. schema-design.md（データ構造・フィールドの意味に迷ったとき）
3. atmosphere-media-guide.md（動画の採用・不採用判断）
4. Backlog.md（次に何をやるか）
5. template-design.md / list-design.md（UI仕様）

## 4. 情報品質の絶対ルール

- 一次情報（祭り公式＞自治体＞観光協会＞地域団体＞信頼メディア＞個人投稿）を優先する
- 検索結果の要約・スニペットだけで publisher 等を確定させない
  （必ず一次ページを直接確認する）
- 確認できないものは null / unconfirmed / 候補保留で扱う。推測で埋めない
- 「動画なし」「highlightCommentなし」は不足ではなく正常な状態

## 5. schema変更の相談ルール

- フィールドを追加する前に「複数祭りで本当に必要か」
  「既存項目で表現できないか」「運用負荷が増えないか」を確認する
- 二重管理になる構造（priorityフィールド等）は追加しない

## 6. 実装フロー（2026-07-29改訂）

1. Claudeが目的・要件・データ設計を整理する
2. Claudeが既存research・schemaとの整合を確認する
3. ClaudeがCodex向けの実装プロンプト（または調査依頼）を作る
4. Codexが実装・調査・ブラウザ確認・research/data更新・
   commit・pushまで行う
5. Claudeが差分・調査結果をUX/UIレビュアーとしてレビューし、
   「VIGOR MATSURIの思想に合っているか」を判断する。必要なら
   Codexへ改善指示を出す
6. Claudeが最終確認をまとめ、Founderへ判断を求める

## 7. 公開前チェック（祭り1件追加時）

- [ ] research/{slug}.md に出典・確認日を記録したか
- [ ] constantInfo / yearlyInfo が正しく分離されているか
- [ ] true/false/null/"n/a" を正しく使い分けたか
- [ ] atmosphereMediaは採用基準（不採用基準含む）を通過したか
- [ ] sitemap.xml へ、そのページ分の`<url>`エントリを既存テンプレートで
      追記したか（2. 変更範囲の例外ルールに従う。追記のみ、他エントリは
      触らない）

## 8. 公式一次情報に基づく既存ページ更新の委任（2026-10-23 試行運用開始）

Claude MATSURI PMは、下記の条件内に限り、既存の祭りページを公式一次情報に基づいて
自律的に更新してよい（1節・6節の「Claudeは自らコードを書かない」方針に対する、
祭りデータ更新に限った例外。コード・workflow・Scheduled Taskの変更は含まない）。
**最初の2週間（2026-10-23〜2026-11-06）は試行運用**とし、
終了時にFounderが継続・修正・拡大を判断する。

### 8-1. 試行条件

- 1日最大5祭りまで（超える場合はFounder承認）
- 1祭り1コミット（`git revert`で個別に取り消せる単位）
- 更新後は都度Founderへ報告し、週次でも集計して報告する
- Founderは週次で最大3件を抜き取り確認する
- 既存の自動化・Scheduled Task（日次cron、週次保守等）の権限は変更しない。
  通常のended化は引き続き日次cronが担当する
- 期間終了時に、更新件数・検証結果・差し戻し件数・判断に迷った事例をまとめて
  Founder Reviewへ提出する

### 8-2. 自律実行してよい更新

次の**条件をすべて満たす場合に限る**：

- 祭り公式・自治体・観光協会・神社等の一次情報を、**原文（ページ本文・PDF原文）で
  直接確認した**（ツールの要約・検索スニペットのみは不可）
- **年度が明示されている**
- 既存のフィールド・書式で表現できる

対象：

- `schedule`、`access.parkingNote`、`confirmation`（出典・確認日・注記）の追加・更新
- 公式出典URLの追加・移転先への差し替え
- 公式に明示された駐車場情報に基づく`hasParking`の変更
  （meta description等の駐車場表現と、ハブへの反映を同じコミットで揃える）
- 事実を変えない誤記・表記の修正
- 必要な派生ファイル（静的HTML・ハブ・検索インデックス）の再生成
- 通常の開催時刻の更新

### 8-3. 時刻とJSON-LDの扱い

- 公式が「予定」「目安」としている時刻は、確定した開始時刻としてJSON-LD
  （`subEvent`）に出さない。生成ロジックは`H:MM`形式の時刻を`subEvent`として
  出力するため、目安・予定の時刻は「頃」「〜」を付けて非出力にする
- 公式が固定の時刻として示すものだけを`H:MM`で書く（`subEvent`に出る）
- 出典間で情報が食い違う項目は書かず、`confirmation.note`に残して報告する
- 判断が曖昧な場合は実装せず、報告する

### 8-4. Founder承認が必要な更新

- 年度記載のない情報、複数年で未検証の「例年の傾向」の掲載
- **開催日（`dates`の変更）・開催年度の変更**
- **中止・延期・休止に関わる変更**（`cancelled` / `off_year` / 延期など）
- **日程変更に伴うSEO・JSON-LD・自動ended化への影響がある変更**
- 2027年の`yearlyInfo`追加と、それに伴う表示・タイトルの変更
- タイトル・H1・meta descriptionの方針変更（`hasParking`連動の文言を除く）
- 共通テンプレート・スキーマ・生成ロジック・JSON-LD出力仕様の変更
- 掲載の削除・URL変更・非公開化
- 動画・背景画像・見どころ文（`highlightComment`）の新規採用
- 宿泊CTAなど収益導線・外部リンクの追加
- 1日6祭り以上、または全件規模の更新
- 非公式情報源の採用、一次情報同士の食い違いの裁定
- 新規祭り追加（既存の運用に従う）
- 本節の委任ルール自体の変更

### 8-5. 原則禁止する更新

- 一次情報でない出典（まとめサイト・SNS・検索スニペット・ツールの要約のみ）に
  基づく更新
- PDF・画像の内容を、原文を確認せずに転記すること
- 推測・計算による未発表日程の確定表示、未確定情報を確定として表示すること、
  およびJSON-LDに出すこと
- 年度不明の情報を当年の情報として掲載すること
- 過去の実績の上書き・削除、履歴の書き換え（force push等）
- 一括置換・事前相談なしの大規模変更
- `matsuri/`以外（`.github`・root・`tools/`・`assets/`）の変更
- 目安時刻を確定時刻として構造化データに出すこと

### 8-6. 更新前後の検証（毎回）

1. 一次情報を原文で確認し、年度・数値・時刻を転記元と照合する
2. `node matsuri/scripts/check-data-integrity.js`でhard issue 0件を確認する
3. JSON-LDの差分を確認する（`subEvent`が想定どおりか）
4. 派生ファイル（静的HTML・ハブ・検索インデックス）の差分が想定範囲だけであること
5. ローカルで表示を確認する（横スクロールなし）
6. commit・push後、本番反映を確認する
7. `confirmation`に確認日・出典・注記を残す

### 8-7. 報告

- 更新後は都度Founderへ報告する：祭り名、変更フィールド、一次情報、
  検証結果、不採用にした情報、commit hash
- 週次で集計する（更新件数、差し戻し件数、判断に迷った事例）
