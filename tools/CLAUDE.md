## 新規ツール追加基準

新しいツールは `../VISION.md` の Tool Principles 8つを全て満たすか確認する。

```
1. 一つの決断、一つのツール
2. 整理はする。決断はしない。
3. 否定しない、先送りする
4. 必ず「次の一歩」で終わる
5. 5分で終わる
6. ログイン不要、保存は任意でローカルのみ
7. 判定ロジックと広告を分離する
8. 数字を出すツールは前提と責任範囲を明記する
```

評価は5軸で行う（`../VISION.md` 準拠）。

- ブランドへの貢献度
- 検索流入期待
- リピート利用期待
- 関連リンク活性化（何本と繋がるか）
- VIGOR TOOLSらしさ（Tool Principles 8つを満たすか）

**「作りやすいか」は評価軸に含めない。**

現在は「育てるフェーズ」のため、新規提案はまずBacklog.mdへ追加し、
Founder Reviewの結果を踏まえて検討する。すぐに実装へは進まない。

## 改善判断基準

既存ツールの分類（育てる／守る／置いておく）は `Backlog.md` を参照。

- 「育てる」：優先的に改善投資する対象。
- 「守る」：現状維持が絶対条件ではない。思想を壊さない範囲での改善・
  関連ツールへの中立導線までは可能。
- 「置いておく」：公開継続・追加投資はしない。反応があれば再評価する。

この分類自体が仮説であり、実データで随時見直される前提であることを
忘れない。

## データ設計方針

- ログイン不要、サーバーサイド保存なし。**localStorageのみ**。
- **判断履歴**（結果の最新1件を記録）と**共通データ（Profile）**（入力値の
  再利用）は別物。混同しない。
  - 判断履歴：ツールごとの最新の結果1件のみ。時系列・トレンドは持たない。
  - Profile：月々ほぼ変わらない数値のみ対象。貯蓄額・資産残高のような
    変動する数字、年齢・名前のような個人属性は保存しない。

## shared機能利用ルール

`tools/shared/` の共通機能を優先利用する。

- `shared.css`：共通スタイル
- `shared-history.js`：判断履歴の保存・表示
- `shared-profile.js`：共通データ（Profile）の保存・参照
- `card-status.js`：トップページの進捗バッジ表示

### Profile Platform Guard Rails（`shared-profile.js` 準拠）

新しいフィールドを追加する前に、以下を確認する。

1. Profileは目的ではなく手段。育てるためにフィールドを追加しない。
2. ダッシュボード・一覧画面は作らない。文脈付きで個別ツール内にのみ表示。
3. 新フィールドは「今すでに2つ以上の実在するツールが、その数値の入力欄を
   持っている」場合にのみ追加する。「将来使うかもしれない」は理由にならない。
4. 新フィールドを作るより、既存入力値の再利用を優先する。
5. 保存は常にユーザーの明示的操作でのみ行う。自動保存はしない。
6. 保存するのは月々ほぼ変わらない数字だけ。
7. 各フィールドは独立保存し、合算済み数値で上書きしない。
8. データには必ず更新日を表示し、古い数字を黙って使い回さない。

## commitルール

- コミットメッセージは日本語。
- prefix形式を使う：`add:` `fix:` `improve:` `refactor:` `docs:` `seo:`
  `ui:` `update:` など、変更の性質を先頭に明記する。
- 1コミット1意図。複数の意図が混ざる場合は分割する。
